# Truway Docs

Source of the public documentation of [Truway](https://truway.xyz), published with GitBook.
GitBook syncs from this repository through Git Sync: what is merged into `main`
is what the site shows.

Truway traces payments, their distribution and their impact at the last mile, on Stellar. Its
segment is public money executed by third parties: a government agency signs a contract, an
executing organisation spends it, and anyone can check each expense against its budget line.

> **Status: work in progress.** The site is being rewritten from scratch for the public sector and
> for [Proof of Spend](https://github.com/truway-xyz/soroban-contracts/blob/main/docs/proof-of-spend.md).
> It is not published yet. Pages that are not written carry a notice, their intent and what they
> must cover. Technical pages in Spanish are summaries of the English ones for now.

## Structure

One site with two language variants. Each variant is a GitBook space with its own `SUMMARY.md`,
organised in the same four groups.

| Group | For | Written first in | Spanish (`es/`) | English (`en/`) |
|---|---|---|---|---|
| **Conoce Truway / About Truway** | Everyone | Both | `conoce-truway/` | `about/` |
| **Sector público / Public sector** | Government agencies, executing organisations, citizen oversight | Spanish | `sector-publico/` | `public-sector/` |
| **Proof of Spend** | Implementers and readers of the standard | English | `proof-of-spend/` | `proof-of-spend/` |
| **Arquitectura y Stellar / Architecture and Stellar** | Technical reviewers and developers | English | `arquitectura/` (summaries) | `architecture/` |

`gitbook-docs.yaml` declares the two spaces. The four parts are groups and not GitBook sections
because sections need a paid plan; if the site moves to one, each group becomes a section without
moving any file.

### Generated pages

Two kinds of content are never edited by hand:

| Page | Generated by | From |
|---|---|---|
| `*/proof-of-spend/specification.md`, `especificacion.md` | `scripts/sync-spec.sh` | [`soroban-contracts/docs/proof-of-spend.md`](https://github.com/truway-xyz/soroban-contracts/blob/main/docs/proof-of-spend.md) |
| The table in `*/architecture/deployments.md`, `despliegues.md` | `scripts/deployments-table.sh` | [`soroban-contracts/deployments/`](https://github.com/truway-xyz/soroban-contracts/tree/main/deployments) |

Run both from this folder with `soroban-contracts` checked out next to it:

```bash
scripts/sync-spec.sh ../soroban-contracts
scripts/deployments-table.sh ../soroban-contracts
```

The standard is maintained next to its reference implementation and its conformance tests. To
change it, open a pull request in `soroban-contracts`, then run the script here.

## Two vocabularies, on purpose

**Public sector** pages never say *blockchain*, *wallet*, *on chain*, *token*, *hash* or *Stellar*.
They say public record, verification code, document fingerprint. The people who use Truway should
not have to learn infrastructure vocabulary to account for public money.

**Architecture** and **Proof of Spend** pages do the opposite: the more specific, the better.
Contract IDs, SEP numbers, error codes, ledger counts, links to the exact line of code.

The glossary in About Truway maps one vocabulary to the other. Check it before writing a public
sector page.

## Rules for every page

1. **State what is real.** Every page that describes the product carries one label: *Live on
   testnet*, *Built, not deployed*, *Design* or *Roadmap*. Nothing is on mainnet today.
2. **Publish the limits.** Trust model pages list what each party can and cannot do, and what a
   record proves and does not prove, including the uncomfortable rows.
3. **Generate verifiable data, never copy it.** Contract IDs, WASM hashes and commits come from
   [`soroban-contracts/deployments/`](https://github.com/truway-xyz/soroban-contracts/tree/main/deployments)
   through a script.
4. **Back every technical claim** with a version, an identifier, a parameter or a link to the code.
5. **Diagrams as text** (Mermaid or ASCII), never as images without text, so people with screen
   readers and AI agents can read them.
6. **No unconfirmed claims:** no prices, no traction figures, no testimonials and no named
   institutions without written confirmation.
7. **No personal data.** Payees appear as hashes or addresses; examples use demo data and say so.
8. **Spanish and English are rewritten, not translated literally.** Keep both variants in sync in
   the same pull request when possible.

## Style

- One idea per paragraph, short sentences.
- Procedures are numbered and start with the result the reader wants, not with the interface.
- Real screenshots only, never mockups. Demo screens show the *Testnet* and *Demo data* labels.
- Technical pages follow this outline:

  ```markdown
  # Title
  One sentence: what it does and which part touches money.
  > Status: Live on testnet · Built · Design · Roadmap

  ## How it works
  ## What lives on the ledger and what lives off it
  ## Who signs what
  ## What it proves and what it does not
  ## References
  ```

## Contributing

1. Branch from `main` and edit the Markdown files. Never commit to `main` directly.
2. Write commits in English with [Conventional Commits](https://www.conventionalcommits.org/)
   (`docs(architecture): add trust model`).
3. Open a pull request. GitBook syncs once it is merged.

Edits made in the GitBook editor arrive here as commits from GitBook. Review them like any other
change.

## For AI agents

Once published, GitBook serves `llms.txt`, a Markdown version of every page and an MCP endpoint for
the site. They are read only: nothing that moves money or signs anything goes through them.
